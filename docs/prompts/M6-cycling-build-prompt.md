## 1. 用户的实际情况
- 骑行用 **Garmin Edge 830** 码表，配**心率带**和**功率计**。
- 大约一半的骑行，同时在 Apple Watch 上开了运动；另一半没开。
- Garmin Connect 会把骑行训练写进 Apple Health（来源的 Bundle ID 以 `com.garmin` 开头）。它写入的训练里**有没有心率样本，目前还不确定**，代码必须同时兼容“有”和“没有”两种情况。
- 码表**不会**写入睡眠、步数或全天心率，所以**骑行时段以外**的数据不存在重复计数问题。

由此可以得到三种数据来源：
| 来源 | 内容 | 出现频率 |
|---|---|---|
| S1 Apple Watch 骑行训练 | 手表心率（如果心率带通过蓝牙连接了手表，就是心率带的数据）；可能有 `cyclingPower`、`cyclingCadence`、`cyclingSpeed` | 约一半的骑行 |
| S2 Garmin 写入的训练 | 训练记录、距离、能量；心率样本可能有，也可能没有 | 每次骑行 |
| S3 FIT 文件导入 | 逐秒的心率、功率、踏频、速度、海拔、GPS | 用户手动导入 |

## 2. 骑行合并与去重

### 2.1 骑行分组（RideGroup）
- 候选：HealthKit 中类型为骑行的训练（全部来源），加上导入的 FIT 骑行。
- 任意两条候选，如果时间重叠 ≥ 较短者时长的 50%，就归入同一组（取传递闭包）。
- 一组 = 一次骑行。训练列表、负荷、PMC 中都只出现**一次**。
- 组的起止时间 = 各成员起止的并集。

### 2.2 字段级的来源优先级
| 字段 | 优先级（从高到低） |
|---|---|
| 心率 | S3 FIT → S1 手表训练期间的心率 → S2 Garmin 写入的心率样本 → 手表被动心率 |
| 功率 / 踏频 | S3 FIT → S1 中的 `cyclingPower` / `cyclingCadence` |
| 距离、爬升、GPS | S3 FIT → S2 Garmin → S1 手表 |
| 能量（展示用） | 有功率时：机械功 kJ ≈ kcal → 否则用 S1 的能量 → 否则用 S2 的能量 |

### 2.3 分钟心率时间线的通用去重（同时修正 M3 的实现）
不只是骑行：**同一分钟有多个来源的心率时，只取优先级最高的那一个来源的均值**，绝不把多个来源相加或者混在一起平均。全局优先级如下：
`FIT 导入` > `Apple Watch 训练期间` > `其他 App 训练期间（含 Garmin）` > `Apple Watch 被动采样` > `其他`
这样负荷天然只会计算一次。实现时要加回归测试，证明重叠的骑行不会让 TRIMP 翻倍。

### 2.4 心率缺失时用功率补负荷
骑行中有 ≥ 5 分钟连续没有心率（比如心率带掉线），但是有功率时：
1. **优先**：用个人回归模型 `HR = a + b · P30`（P30 = 30 秒滑动平均功率）估算心率，再计算 TRIMP。启用条件：历史上同时有心率和功率的配对秒数 ≥ 1200，且 R² ≥ 0.5。另外要加上心率滞后：P30 往后平移 20 秒再拟合。
2. **其次**：训练负荷 = k · TSS，k = 历史骑行中“TRIMP ÷ TSS”的中位数（至少需要 5 次骑行）。
3. 两者都不满足：这段时间按空窗处理，并在骑行卡片上标注“心率缺失，负荷可能低估”。

**负荷的口径保持不变**：每日负荷依然以心率 TRIMP 为准，保证所有运动可比。功率只用于骑行的专项指标（§3），以及上面的缺失补偿。

## 3. 骑行专项指标（新增到 `VigorScoring/Cycling/`）

| 指标 | 定义 |
|---|---|
| 平滑功率 | 1 Hz 序列，暂停期间按 0 填充；先算 30 秒滑动平均（从第 30 秒开始），再求四次方的均值，最后开四次方 → NP |
| FTP | 用户手动设置 > HealthKit 中的 `cyclingFunctionalThresholdPower` > 自动估算：最近 90 天最佳 20 分钟平均功率 × 0.95 |
| 强度系数 | IF = NP / FTP |
| 训练压力 | TSS = (时长秒 × NP × IF) / (FTP × 3600) × 100 |
| 机械功 | kJ = Σ 功率 × Δt / 1000 |
| 功率区间（Coggan） | Z1 < 55%、Z2 55–75%、Z3 76–90%、Z4 91–105%、Z5 106–120%、Z6 121–150%、Z7 > 150%（相对 FTP） |
| 功率曲线 | 5 秒 / 1 分钟 / 5 分钟 / 20 分钟 / 60 分钟的最佳平均功率；单次骑行一条曲线，另外维护最近 90 天的最佳曲线 |
| 功体比 | W/kg，体重取 HealthKit 最新值 |
| 有氧效率 | EF = NP / 平均心率 |
| 有氧解耦 | 只对 ≥ 60 分钟的骑行计算：把骑行按时长对半分成两段，解耦 = (EF前 − EF后) / EF前 × 100%；< 5% 视为有氧基础良好 |
| 体能管理（PMC） | CTL_t = CTL_(t−1) + (TSS_t − CTL_(t−1)) / 42；ATL 同理，时间常数为 7；当天状态 TSB = CTL_(t−1) − ATL_(t−1)。按自然日计算，没骑车的日子 TSS 记为 0 |

- 骑行的 TSS 只用于 PMC 和骑行页，**不进入**恢复和睡眠的计算。
- 心肺适能趋势（PRD §5.12.2）新增两项：EF 的 90 天趋势、90 天最佳 20 分钟功率的变化。

## 4. FIT 文件导入（新包 `Packages/VigorFIT`，只依赖 Foundation）

### 4.1 解析器（按 FIT 协议自己实现，不引入第三方库）
- **文件头**：12 或 14 字节（头长度、协议版本、Profile 版本、数据长度 UInt32 LE、字符串 `.FIT`、可选的头 CRC）。整个文件的 CRC-16 按 FIT SDK 的算法校验，校验失败时报错。
- **记录头**：
  - 普通头：bit7 = 0；bit6 = 1 表示定义消息；bit5 表示定义中带开发者字段；bit0–3 为本地消息类型。
  - 压缩时间戳头：bit7 = 1；bit5–6 为本地类型；bit0–4 为时间偏移。还原方式：`ts = (last & ~0x1F) + offset`；如果 `offset < (last & 0x1F)`，再加 `0x20`。
- **定义消息**：保留字节、字节序（0 = 小端，1 = 大端）、全局消息号 UInt16、字段数、每个字段 3 字节（字段号、大小、基本类型）；带开发者字段时，还有开发者字段数 + 每个 3 字节——**读取后跳过**。
- **无效值**：uint8 为 0xFF，uint16 为 0xFFFF，uint32 为 0xFFFFFFFF，sint32 为 0x7FFFFFFF，均视为缺失。
- **时间基准**：FIT 纪元为 1989-12-31 00:00:00 UTC，等于 Unix 时间 631065600。
- **需要读取的消息与字段**：
  | 消息（全局号） | 字段 |
  |---|---|
  | `file_id`（0） | 1 制造商、2 产品、3 序列号、4 创建时间 |
  | `session`（18） | 2 开始时间、5 运动类型、7 总耗时（毫秒，除以 1000）、9 总距离（厘米，除以 100） |
  | `lap`（19） | 起止时间（可选，用于分圈展示） |
  | `record`（20） | 253 时间戳、0/1 经纬度（半圆单位，× 180 / 2³¹）、2 海拔（uint16，÷5 − 500）、3 心率、4 踏频、5 距离（÷100）、6 速度（÷1000）、7 功率、73 增强速度（÷1000）、78 增强海拔（÷5 − 500） |
  | `event`（21） | 计时器的开始 / 停止，用于识别暂停 |
- 不认识的消息，按定义的长度跳过。
- **输出**：`RideStream`，包含 1 Hz 对齐的数组（时间、心率、功率、踏频、速度、距离、海拔、经纬度，缺失为 nil）、暂停区间、设备信息，以及 `fileID = 序列号 + 创建时间`（用于去重）。

### 4.2 导入方式
- 在“文件”App 中多选导入（`.fileImporter`，允许多选）。
- 系统分享面板中的“用元气打开”：在 Info.plist 中声明 `CFBundleDocumentTypes` 和导入的 UTType（扩展名 `fit`，遵循 `public.data`）。
- 文件夹导入：选择一个目录，递归导入其中全部 `.fit` 文件。用户可以尝试把 Edge 830 通过 USB 连接 iPhone 后，选择码表上的 `Garmin/Activity` 目录（能不能识别取决于设备，不保证可用）。
- 以 `fileID` 去重，重复导入时直接跳过，并提示“已导入”。

### 4.3 存储
- 原始 FIT 文件保存在 `Application Support/FIT/<fileID>.fit`；解析结果和逐秒数组保存为 SwiftData 模型 `ImportedRide`（嵌套数据以 JSON 或压缩二进制 `Data` 保存）。
- **FIT 数据无法从 HealthKit 重建**，所以必须纳入备份（PRD §9.4）。
- **不要把 FIT 骑行写回 HealthKit**，否则会产生第三份重复数据。

## 5. 数据层与流水线的改动
- 实时数据源增加读取 `cyclingPower`、`cyclingCadence`、`cyclingSpeed`、`cyclingFunctionalThresholdPower`（这些标识符已在 SDK 中确认）。
- 快照升级到 schema v3：新增 `cyclingPower`、`cyclingCadence`、`cyclingSpeed`、`ftp` 样本数组，以及可选的 `importedRides: [RideStream]`。要能读取 v1 和 v2 的快照。
- `PipelineInput` 增加导入的骑行；`PipelineOutput` 增加骑行分组、每次骑行的指标、功率曲线、PMC 序列。
- **合成场景 v3**：在 v2 的基础上，每周增加 2–3 次骑行（60–180 分钟，带功率），按序号分配四类情况，保证确定性：
  1. 手表训练 + Garmin 训练 + FIT 文件三者都有；
  2. 只有 Garmin 训练（不带心率样本）+ FIT 文件；
  3. 只有 Garmin 训练（不带心率样本），没有 FIT 文件；
  4. 手表训练 + Garmin 训练，其中有一段 10 分钟心率掉线。
  FIT 文件用测试辅助工具中的 FIT **编码器**生成（见 §7），保证可以端到端测试。
- **注意**：本阶段很可能让黄金快照发生变化，变化原因要写进 `DECISIONS.md`，然后再更新黄金文件。

## 7. 测试（期望值必须精确）

| 测试 | 期望 |
|---|---|
| NP（恒定功率） | 200 W 持续 1 小时 → NP = **200** |
| NP（变功率） | 300 W 30 分钟后接 100 W 30 分钟 → NP ≈ **253.0**（±2，过渡段的影响） |
| IF / TSS | NP 200，FTP 250，1 小时 → IF = **0.8**，TSS = **64.0** |
| FTP 估算 | 最佳 20 分钟功率 280 → FTP = **266** |
| 有氧解耦 | 前半段 NP 200 / 心率 140，后半段 NP 200 / 心率 147 → **4.76%**（±0.01） |
| PMC | 从 0 开始，连续 42 天 TSS 恒为 100 → CTL = 100 × (1 − (41/42)^42) ≈ **63.65**（±0.02） |
| 骑行分组 | 重叠 60% → 同一组；重叠 30% → 两组 |
| 分钟去重 | 同一次骑行同时有 FIT 和手表训练的心率 → 该时段的 TRIMP 等于只用 FIT 计算的结果（**不会翻倍**） |
| 心率优先级 | 某一分钟同时有手表训练心率和 Garmin 心率 → 取手表的 |
| 功率补偿 | 掉线 10 分钟，并且回归模型可用 → 用估算心率计算 TRIMP；模型不可用、k 也不可用 → 打上“负荷可能低估”的标记 |
| FIT 往返 | 用测试中的 FIT 编码器生成文件（含压缩时间戳头、开发者字段、大端定义、无效值）→ 解析后与原始数据逐字段相等 |
| FIT CRC | 改动一个字节 → 解析报错 |
| FIT 去重 | 同一个文件导入两次 → 只保留一条 |
| 真实文件（可选） | 如果 `Packages/VigorFIT/Tests/Fixtures/real/` 中有 `.fit` 文件，就解析它，并断言记录数 > 0、时间单调递增；没有文件时跳过这个测试 |

## 9. 给用户的使用建议（写进 BUILD-REPORT 的 M6 一节）
- 如果你的心率带和功率计支持 ANT+ 和蓝牙**同时连接**，可以把它们也通过蓝牙配对到 Apple Watch（在手表的“设置 → 蓝牙”中）。这样在手表上开运动时，心率带的心率和功率计的功率会直接写入健康数据，不需要再导入 FIT。注意：部分功率计限制蓝牙连接数，可能需要先断开手机上的其他 App。
- 没开手表运动的那一半骑行：导入 FIT 是最完整的方案。可以从 Garmin Connect 网页版的活动页面“导出原始文件”（得到包含 FIT 的 zip，解压后导入），或者从码表的 `Garmin/Activity` 目录拷出来。
